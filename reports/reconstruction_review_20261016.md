## Что проверено и как читать замечания

- **Воспроизведено**: ошибка или механизм проверены локальным вызовом.
- **Установлено по коду / источнику**: найдено прямое расхождение в пути
  исполнения или определении; величина его влияния на DCM не измерена.
- **Гипотеза**: объяснение результата, для которого ещё нужен эксперимент.

P1 означает блокировку запуска или заявленного научного сравнения. P2
означает проблему воспроизводимости, контроля эксперимента или конкретного
сценария запуска. Приоритет не оценивает размер возможного выигрыша метрики.
Часть дефектов существовала до двух проверяемых коммитов.

Источники вне этого репозитория лежат рядом с ним в рабочем дереве HGND:

- [эталонный training notebook](../../NeutronRecoGNN/notebooks/EgdeClass_Cluster_Jan25-xecs.ipynb);
- [ноутбук оценки `results_Jan26_wtest`](../../results_Jan26_wtest.ipynb);
- [доклад Dombay от 26.02.2026](../../NeutronRecoGNN/docs/VB_BMN_Dombay.pdf),

Привязка фактически опубликованных графиков к конкретным весам и версии
ноутбука ещё требует проверки. Ниже явно указано, что подтверждает локальная
копия источника, без приписывания ей неизвестного checkpoint.

## DCM-01 · P1 · Фабрика модели отвергает новые параметры архитектуры

**Статус: воспроизведено.** Дефект интеграции новых флагов.

Путь вызова: `scripts/train.py:258–264` → `models.get()` →
`models/default_net_registration.py:16–19` → `build_default_net()`.
Фабрика принимает только `dataset`, `hidden_channels` и `num_layers`.
Параметры `cluster_size_feature`, `cluster_pooling` и `hit_residual` до
конструктора не доходят: Python отвергает их при входе в фабрику.
Тот же путь используется при восстановлении модели в `scripts/evaluate.py`.

Минимальная проверка из корня HGNDRecoGNN, без данных и kNN:

```bash
python - <<'PY'
import sys
sys.path.insert(0, '..')
from HGNDRecoGNN import models

for flags in (
    {'cluster_size_feature': True},
    {'cluster_pooling': 'mean_max_sum'},
    {'hit_residual': True},
):
    try:
        models.get('net_default', None, **flags)
    except TypeError as exc:
        print(flags, exc)
PY
```

Для каждого словаря получено `_factory() got an unexpected keyword argument`.
Варианты `size`, `pool`, `residual` падают до обучения, после подготовки данных.

`tests/test_train_cli.py:72–85` проверяет сигнатуру `Net.__init__`.
Проверки argv останавливаются после разбора аргументов. Поэтому ни одна из
них не проверяет фактический вызов фабрики.

**Условие закрытия:** фабрика принимает и передаёт параметры; тест проходит
через настоящий реестр и проверяет свойства созданной модели. Дополнительно
нужно проверить восстановление каждого варианта через путь оценки и
выполнить smoke run с настоящим kNN на тестовом разделе кластера.

## DCM-02 · P1 · Метрики сравнения с Dombay имеют разные определения

**Статус: установлено по коду и первоисточнику.** Несогласованность оценщика
существовала до новых флагов; новый аудит использует её для численного вывода.

В `scripts/reco_performance.py:46–65` вычисляются:

```text
purity_energy = 1 - sum(e_pred у выбранного фона) / sum(e_pred у выбранных)
efficiency_energy = sum(e_true у выбранного сигнала) / sum(e_true у сигнала)
```

Выбираются все кластеры выше порога. Знаменатель эффективности построен по
сигнальным кластерам, без идентификации уникальных MC-нейтронов.

На слайде 16 Dombay графики подписаны `3 best clusters per event`.
В соответствующем локальном ноутбуке оценки:

- ячейка 89 оставляет один hit на кластер, затем три лучших кластера на `Row`;
- ячейка 93 строит гистограммы в диапазоне 0–6 GeV и вычисляет
  `eff = counts1 / counts0`, `pur = 1 - counts3 / counts2`;
- `counts0` строится по MC-нейтронам после `groupby(['Row', 'Id'])`.

Обозначения спектров `E_true` и `E_predicted` на слайде сами по себе не
означают суммирование энергии записей. Локальная реализация использует числа
записей в энергетических бинах. Способ получения подписанных усреднённых
значений 80%/87% из этих кривых ещё нужно восстановить.

Есть отдельное расхождение energy resolution: ячейка 42 ноутбука считает
стандартное отклонение относительной ошибки, а
`scripts/reco_performance.py:79–88` использует половину интервала 16–84%.
Отличается и отбор по cluster score.

**Следствие:** разрыв эффективности «11–14 процентных пунктов» пока не
установлен для одного и того же оценщика. Это замечание не опровергает
отдельно измеренный ROC AUC, но сопоставимость его выборок тоже надо проверить.

**Условие закрытия:** зафиксировать выбор кластеров, определение MC-сигнала,
знаменатель, энергетический диапазон, агрегирование по бинам и оценщик
resolution. Применить один протокол к эталонным и новым предсказаниям.
Собственные метрики с суммами энергий можно сохранить под отдельными именами.

## DCM-03 · P1 · Вариант `ref` отличается от названного эталона по архитектуре

**Статус: последовательность вызовов эталона воспроизведена трассировкой.**
Расхождение предшествует новым флагам и не перечислено среди двух заявленных
отступлений в заголовке `slurm/train_dcm.hpc.sbatch`.

В ячейке 51 `EgdeClass_Cluster_Jan25-xecs.ipynb` при `num_layers=8` создаются
восемь свёрток и четыре BatchNorm. Но `forward` содержит:

```python
for conv, batch_norm in zip(self.convs[:-3], self.batch_norms):
    x = conv(x, edge_index)
    # x = batch_norm(x)
    x = x.relu()
```

`zip` выполняет четыре итерации: две EdgeConv и две SAGEConv. После него
вызываются две GraphConv. Итого реально работают шесть свёрток, BatchNorm
не вызывается. Трассировка тела `forward` подтвердила этот порядок.

В `models/default_net.py:215–232` работают две EdgeConv, четыре SAGEConv с
BatchNorm и две GraphConv. Совпадение параметра `num_layers=8` не означает
совпадения исполняемой архитектуры. Входы тоже различаются: список features
эталона содержит девять признаков, текущий cache добавляет `SurfaceHit`.
Дополнительный cluster-link loss уже отмечен исходным аудитом.

Также в докладе указано окно 1.5 ns, а в названном training notebook задано
1.0 ns. Эти значения здесь приведены как настройки источников; новый выбор
окна этим отчётом не предлагается.

**Условие закрытия:** установить версию кода, данных и весов, породившую
публикуемые benchmarks. Разделить точное воспроизведение этого источника и
baseline текущего pipeline; описать все намеренные различия между ними.

## DCM-04 · P1 · Validation повторно используется как финальный test

**Статус: установлено по пути исполнения.** Существующая проблема протокола;
особенно существенна при последовательном выборе вариантов модели.

`training/train.py:135–150` создаёт две части данных. `fit()` вычисляет loss
на второй части и при `save_best_on='val'` выбирает по ней checkpoint
(`training/train.py:330–357`). Затем `scripts/evaluate.py:153–156` с теми же
seed и долей train восстанавливает эту же вторую часть под именем `test`.
`scripts/reco_performance.py:114–118` ещё и выбирает рабочий порог на
оцениваемых данных по близости purity к 87%.

Оценка кривой efficiency/purity на validation допустима для разработки.
После выбора эпохи, архитектуры и порога эта выборка не является независимым
финальным test. Величина оптимистического смещения не измерена.

**Условие закрытия:** сохранять отдельные train/validation/test event IDs.
Эпоху, архитектуру и рабочий порог выбирать на validation; зафиксированную
процедуру оценивать на test. Режим исторического воспроизведения с двумя
частями обозначать отдельно.

## DCM-05 · P2 · Две половины одного столкновения расходятся между split

**Статус: механизм воспроизведён на локальном cache.** Существующий дефект
разбиения для оценки переноса на новые столкновения.

`data/graph_dataset.py` строит отдельные top/bottom графы с одним `Row`.
`split_dataset()` случайно делит индексы графов без группировки по `Row`.
Поэтому часть столкновения может участвовать в обучении, а другая в оценке.

Проверка выполнена на старом локальном SMASH defaultSpot cache:
`notebooks/cache/ndet_dataset_smash_defaultSpot/processed`, 200000 графов.
В `shard_0.pt` и `shard_98.pt` найдены 819 полных top/bottom пар по `Row`;
при штатном split seed 42 у 403 пар половины попали в разные части.
Это техническая проверка разбиения на исторических данных, не новый
физический результат и не оценка размера смещения на DCM.

**Условие закрытия:** делить уникальные столкновения и назначать обе половины
одной части. Проверять отсутствие общих event IDs между частями. Если `Row`
не глобально уникален, ключ должен включать идентификатор источника.

## DCM-06 · P2 · Seed устанавливается после инициализации модели

**Статус: порядок вызовов и различие начальных весов воспроизведены.**
Существующий дефект CLI, не устранённый подготовкой лестницы.

`scripts/train.py:264` создаёт модель. `torch.manual_seed(cfg.seed)` вызывается
позже, при split и в `fit()` (`training/train.py:137,285`). Он фиксирует
последующие случайные операции, но не уже созданные веса, включая ленивую
инициализацию при dummy forward.

Два вызова CLI с `--seed 42` и заменёнными тяжёлыми операциями дали разные
начальные веса простой Linear-модели. Реестр в этой проверке заменялся только
для наблюдения момента инициализации; это не запуск настоящей GNN.

**Условие закрытия:** устанавливать seed до создания и материализации модели.
Проверять равенство начальных state_dict при одинаковых аргументах в отдельных
процессах. Seed разбиения и seed обучения хранить отдельно, чтобы повторения
обучения не меняли одновременно test. Для resume сохранять состояние RNG.

## DCM-07 · P2 · Отдельная сборка scaler-кэшей меняет случайное размытие

**Статус: механизм воспроизведён на искусственных CSV.** Существующая
проблема контроля сравнения `SCALER=own` и `SCALER=smash`.

`slurm/preprocess_dcm.hpc.sbatch` создаёт разные корни для этих режимов.
`HGNDGraphDataset.process()` вызывает `load_hits()` с cache_dir внутри
собственного корня (`data/graph_dataset.py:761–766`). При отсутствии parquet
каждый вызов заново добавляет `np.random.normal(0, 0.15, len(df))`
(`data/graph_dataset.py:373–374`), без сохранённого seed.
Размытое время затем участвует в prompt-разметке и построении графа.

Проверка с одними искусственными CSV и двумя пустыми cache_dir дала разные
времена и разные prompt-метки. Искусственные энергии были расположены у
границы prompt-условия, чтобы проверить механизм. Доля изменившихся меток в
этом примере не оценивает эффект на реальных данных. Установить, различались
ли так уже существующие кластерные кэши, можно только проверкой их содержимого.

**Условие закрытия:** использовать одну сохранённую реализацию размытия и
одни event IDs для обоих режимов. Перед сравнением проверить одинаковость
hit keys, физических времён, меток и структуры графов. Меняться должна только
стандартизация признаков. Можно переиспользовать affine-преобразование
`--restandardise-to` вместо повторного случайного preprocessing.

## DCM-08 · P2 · Ступень `budget` одновременно меняет три фактора

**Статус: установлено по dispatch в job script.** Проблема новой постановки.

`slurm/train_dcm_improve.hpc.sbatch:74–79` меняет 25 эпох на 30,
MultiStepLR на cosine и добавляет три эпохи warmup. Результат сравнения
измерит совместное действие этих изменений. Он не отделит эффект числа
шагов от scheduler и warmup.

При одинаковых данных и batch 256 число шагов в `budget` относительно `ref`
растёт примерно в `30/25 = 1.2` раза, с поправкой на последний batch.
Упомянутое в аудите отношение 2.5 относится к другому сравнению:
25 эпох при batch 256 против 20 при batch 512. Оно не характеризует
переход между двумя подготовленными ступенями.

**Условие закрытия:** либо назвать `budget` экспериментом над пакетом настроек
и ограничить вывод этим пакетом, либо добавить контроль с изменением только
числа эпох, затем scheduler, затем warmup. Сравнивать на одинаковых данных,
разбиении и согласованном наборе training seeds. Заранее записать целевую
метрику, ожидаемое направление эффекта и правило выбора следующей ступени.

## DCM-09 · P2 · Resume может соединить веса и Adam из разных эпох

**Статус: воспроизведено с имитацией прерывания записи.** Существующий дефект,
перенесённый в новый контракт автопродолжения.

В `training/train.py:363–375` сначала атомарно заменяется `optim.pt` с
`next_epoch`, затем отдельно записывается `last.pt`. Между ними возможна
остановка задания. Запись `last.pt` сама по себе также не атомарна.
Shell-script берёт номер эпохи из `optim.pt`, веса из `last.pt` и не проверяет
согласованность (`slurm/train_dcm_improve.hpc.sbatch:127–140`).

В локальной проверке после одной завершённой эпохи была имитирована остановка
перед следующей записью `last.pt`. Получено `optim.next_epoch=2`, тогда как
`last.epoch=0`; для такого `next_epoch` ожидались веса эпохи 1. Проверка
использовала простую модель и заглушки epoch loops, без обучения GNN.

**Условие закрытия:** записывать модель, optimizer, scheduler, эпоху и RNG в
единый resume-файл через временный файл и атомарную замену. Если файлы
раздельные, нужен протокол согласованных поколений и проверка перед resume.
Тест прерывания между записями должен завершаться отказом или восстановлением
согласованного поколения. Для модели без параметрических изменений, например
`hit_residual`, также нужно сравнивать конфигурацию, а не только state_dict keys.

## DCM-10 · P2 · Каталог checkpoint не идентифицирует все настройки запуска

**Статус: установлено по шаблонам путей.** Дефект нового job script.

В `slurm/train_dcm_improve.hpc.sbatch:115` корень данных зависит от `SCALER`,
а каталог checkpoint в строке 117 от него не зависит. В имени также нет
переопределяемых `BATCH` и `NUM_SHARDS`. Разные запуски одного варианта могут
получить один каталог, после чего автопродолжение подхватит чужой optimizer
и веса либо сообщит, что обучение уже завершено.

**Условие закрытия:** сохранять эффективную конфигурацию и идентичность данных,
проверять их совместимость при resume. Включить scaler и идентификатор запуска
в путь либо запрещать повторное использование каталога при несовпадении
конфигурации. Проверить конфликт `SCALER=own` / `SCALER=smash` отдельно.

## DCM-11 · P2 · Предупреждение scheduler падает с одним milestone

**Статус: воспроизведено.** Новый дефект в диагностике scheduler.

`training/train.py:218–228` при недостижимом milestone обращается к
`sorted(cfg.scheduler_milestones)[1]`. CLI допускает один milestone.
Например, при 20 эпохах и `--scheduler-milestones 25` вместо предупреждения
возникает `IndexError: list index out of range`. При `verbose=False` этот
путь не выполняется; штатная конфигурация с тремя milestones не падает.

Минимальная проверка из корня HGNDRecoGNN:

```bash
python - <<'PY'
import sys
sys.path.insert(0, '..')
import torch
from HGNDRecoGNN.training.train import TrainConfig, _build_scheduler

cfg = TrainConfig(epochs=20, scheduler_milestones=(25,), verbose=True)
opt = torch.optim.Adam([torch.nn.Parameter(torch.zeros(1))], lr=cfg.lr)
_build_scheduler(cfg, opt)
PY
```

Числа здесь воспроизводят допустимую конфигурацию, вызывающую ошибку;
рекомендацией по обучению они не являются.

**Условие закрытия:** строить предупреждение без предположения о количестве
milestones. Проверить пустой список, один достижимый, один недостижимый и
несколько milestones при включённом выводе.

## Какие объяснения результатов остаются гипотезами

1. **Влияние energy head.** Малая величина MSE среди значений loss не
   исключает конфликт с классификацией. Нужны нормы и направления градиентов
   отдельных задач на общих параметрах и контрольное изменение веса задачи.
   Исходный аудит использует loss на сохранённых предсказаниях; этого
   недостаточно для исключения механизма во время обучения.
2. **Переобучение и недостаточный бюджет.** `train_loss < val_loss` в одном
   checkpoint не устанавливает переобучение. Лучшая эпоха по training loss
   в конце запуска не доказывает продолжавшееся улучшение validation.
   Нужны полные истории по эпохам и повторения обучения. Сумма LR у Adam
   также не является измерением фактической величины обновления весов.
3. **Oversmoothing и необходимость residual.** Глубина сети сама по себе
   не измеряет oversmoothing. Нужна диагностика представлений по слоям и
   контролируемое сравнение. Standalone AUC размера кластера подтверждает
   наличие информации в признаке, но не измеряет выигрыш от его добавления
   к уже обученной сети, тем более на другом генераторе.

Ожидаемая величина влияния каждого исправления на DCM не установлена.
