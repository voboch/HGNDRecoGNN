## Почему эти AUC нельзя прямо сравнивать с текущим пайплайном

1. **Другие кандидаты.** Студент строит связные компоненты radius/time-графа
   хитов с `R_cells=5`, `dt_edge_ns=2.5` и не сохраняет компоненты из одного
   хита. Параметры унаследованы из его рецепта, не оптимизированы этим аудитом.
   Текущий HGND pipeline использует другой граф и сегментацию, включая
   одиночные кластеры. Вклад этого отбора в разницу AUC не измерен.
2. **Другое время.** Вход — `fTime_nonoise`, дополнительное размытие отключено.
   В том же локальном файле `fTime-fTime_nonoise` имеет SD 0.149978 ns.
   Это не подтверждённая работа с разрешением времени нашего детектора.
3. **Другая разметка.** Положителен компонент, содержащий хотя бы один hit
   с PDG=2112, Side 5/6 и истинной энергией внутри заранее сохранённой
   ToF-полосы. Отсечка `Ekin>0.3 GeV` нашего loader отсутствует: 1726
   положительных хитов лежат ниже или на этой границе. Порог этого аудита
   не менялся; это сравнение двух существующих определений.
4. **Другой рецепт обучения.** Четыре residual layers, LayerNorm, четыре
   pooling-операции, BCE classification, L1 energy regression и minibatch
   event-ranking loss; до 100 эпох, early stopping и выбор checkpoint по
   validation score separation. Наши 30-эпоховые результаты с другой
   архитектурой/лоссом не являются абляцией этого набора изменений.

Прямого поступления `PDG`, `Side`, `Ekin`, `Id` или `n0_label` в шесть
численных признаков не обнаружено. На 32 событиях изменение только MC-полей
оставило `x` и рёбра идентичными; у всех шести моделей изменение target/row
полей не изменило forward. Это ограниченные, конкретные проверки отсутствия
такой утечки, не сертификат происхождения всего датасета.

Сам preprocessing требует MC-колонки и удаляет строки с пропущенными
truth-значениями. Для применения к измеренным хитам нужно отделить вычисление
наблюдаемых признаков от target construction и MC-dependent filtering.

## Подтверждённые проблемы оценки событий

**Batch-dependent event efficiency.** В исходной inference-функции
`baseline_GraphSAGE.ipynb`, ячейка 39, цикл по событиям находится внутри
цикла DataLoader minibatches. Кандидаты одного события могут оказаться
в разных батчах. Вызов самой функции на одном сконструированном событии
с двумя положительными кандидатами дал следующий контрпример.
Nothing is fitted; same weights. No direction is better in this diagnostic
table: ожидается независимость результата от размера батча.

| Размер батча (count) | Посчитанные signal events (count) | Посчитанная event efficiency (dimensionless) |
|---|---|---|
| 1 | 2 | 0.5 |
| 2 | 1 | 1.0 |

Предсказания и событие одинаковы. Это инженерный контрпример, не измерение
качества на DCM. Исправление — сначала собрать все предсказания, затем
группировать по событию целиком. До исправления нельзя переносить event
efficiency/selection score и multiplicity matrices в результаты пайплайна.
ROC-AUC собирается по всем графам отдельно; этот дефект сам по себе его
не завышает.

**Компоненты не равны нейтронам.** В test до дополнительного energy cut
есть 12240 различных `(Row, Id)` сигнальных объектов после hit selection;
в сохранённых компонентах представлены 11162. При этом положительных
компонентов 9857; 1149 из них содержат несколько signal IDs, и встречаются
14 повторных появлений signal IDs в разных компонентах. Эти counts получены
заново из полного локального входа. `n_true=sum(y_cls)` считает компоненты,
а не уникальные нейтроны. `n_matched=sum(selected_true_mask)` не выполняет
взаимно однозначного сопоставления объектов. События без сохранённых графов
вообще не поступают в inference. Полная нейтронная multiplicity response
и efficiency относительно всех сгенерированных нейтронов не установлены.

## Исполнимость и включение в пайплайн

Сохранённый Python-код содержит три блокирующие синтаксические ошибки:

- `Challenger_ufc_DynamicEdgeConv.ipynb`, ячейка 5: не закрыт список `float_cols`;
- `Challenger_ufc_GAT.ipynb`, ячейка 23: две оборванные строки `assert ...,`;
- `baseline_ufc_GAT.ipynb`, ячейка 23: одна оборванная строка `assert ...,`.

Проверочная утилита исправляет только эти места в памяти и записывает repairs
в JSON. Сами тетрадки не правились. В baseline GraphSAGE загрузка также
использует `pd` до видимого импорта; clean-kernel run требует упорядочивания
импортов и замены Colab paths. README ссылается на отсутствующий
`requirements.txt`; графы и checkpoint paths не привязаны к split/source
hashes. Построение шардов дописывает файлы с новым номером при повторном
запуске, поэтому требуется защита от дублирования старого содержимого.

После минимального исправления синтаксиса все шесть архитектур прошли CPU
forward/backward, проверку конечности значений, strict state-dict roundtrip
на случайных весах и сравнение отдельного/батчевого inference для графов
с 2, 8 и 9 хитами. Проверка использовала локальные torch 2.7.1 / PyG 2.7.0,
а не исходный Colab torch 2.4.0. Оригинальные графы в новом torch требуют
явной политики загрузки PyG objects; в сконструированном probe разрешены
только нужные типы PyG через `safe_globals`.

Модели имеют 290691–366403 параметров. Их интерфейс — homogeneous
`Data(x[:,6], edge_index, n_hits)` и дополнительно `pe[:,4]` для spectral
gate; выход — два тензора: logit кандидата и положительная энергия.
Текущий default Net принимает batched HeteroData через свой ModelSpec и
возвращает шесть элементов для hit/link/cluster/energy задач. Поэтому
сохранённый checkpoint студента нельзя загрузить в `net_default`.

Минимальный путь внедрения:

1. Получить оригинальные 18 checkpoints, per-seed CSV, их hashes и соответствие
   исходным данным/splits; пересчитать ROC-AUC каждого seed, не смешивая seeds.
2. Ввести отдельный homogeneous UFC data/model branch с исходными observable
   признаками и label-free inference. Зарегистрировать свой ModelSpec/loss и
   экспорт candidate score/energy с устойчивыми event/candidate IDs.
3. Перенести событийную агрегацию за пределы minibatches; учитывать пустые
   события и делать уникальное truth-object matching для neutron metrics.
4. Сначала воспроизвести исходный рецепт, затем проверить детекторное время
   и source-separated transfer по заранее записанному протоколу. Существующий
   открытый test 988976 не использовать для выбора новой архитектуры.

Для первой интеграции GraphSAGE — удобный технический контроль: модель
прошла probe без исправления своего определения и имеет простую статическую
смежность. DynamicEdgeConv и spectral gate остаются отдельными вариантами;
сохранённые десятые доли процента AUC не устанавливают их преимущество
на нашем наборе или на физической нейтронной реконструкции.
